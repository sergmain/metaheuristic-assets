| workflow | bundle dir | description |
|---|---|---|
| mh-call-cc-1.0 | call-cc | Runs the Claude Code CLI on a prompt taken from a Variable and returns CC's answer verbatim in a Variable. Builds no prompt and parses no answer - the model step inside a larger workflow. |
| mh-dir-batcher-1.3 | dir-batcher | Scans a source-code directory, cuts the list of files worth deriving requirements from into fixed-size batches, and stores each batch as a meta-storage record - a work queue for a requirements pass. |
| mh-rg-temp-project-1.1 | rg-temp-project | Creates a fresh, empty RG project with a random TMP code through the RG REST API (vault key RG_API_AUTH) and reports the code. Optionally sets its description, an RG genesis pipeline and readiness. |
| mh-rg-requirements-from-file-1.1 | rg-requirements | Reads the file named by a meta-storage batch record (the output of dir-batcher), has CC derive requirements from it for a given description, and stores them in a fresh RG project. Uses rg-temp-project and call-cc. |
| mh-rg-requirements-from-batch-1.5 | rg-requirements | Reads every file named by one meta-storage batch record, has CC derive requirements from each file in parallel (one mh.batch-line-splitter branch per file, CC answers cached), and stores them all in a fresh RG project as one chain of snapshots. The run's model/effort are recorded on the RG project (1.5). The record is left in the table (deletion disabled in 1.2). Uses rg-temp-project and call-cc. |
| mh-verify-git-cycle-1-1.2 | verify-git-cycle/scenario-1 | Test fixture for Function delivery: a dispatcher-sourced hello Function's response is upserted into meta storage (mh-verify.git-cycle). No DETAILS.md. |
| mh-verify-git-cycle-2-1.2 | verify-git-cycle/scenario-2 | Test fixture for Function delivery: the same with a git-sourced hello Function, also reporting the payload revision. No DETAILS.md. |
| mh-factorial-main-1.8 | common-bundle | Legacy YAML example (factorial): the entry graph, built on mh.exec-source-code. No DETAILS.md. |
| mh-factorial-recursion-1.17 | common-bundle | Legacy YAML example (factorial): the recursive graph, built on mh.evaluation and mh.nop. No DETAILS.md. |

| nrvv-recovery-1.1 | nrvv | NRVV (needs, requirements, verification, validation): recovers requirements from a repository, writes a test suite per TEST_CASE without seeing target code, implements the target in Python, and verifies it suite by suite. Recovery: checks a repository out, lists its files by glob, has CC derive each file's requirements in parallel, and stores them in one new RG project as one committed snapshot, every Rationale citing repository + revision + file. Started by the Dispatcher for an NRVV recovery request. Test-author, implementation and verification follow. |
| nrvv-test-author-1.0 | nrvv | NRVV test-author: for every requirement in scope at a named RG snapshot, has CC derive ONE pass/fail criterion from the requirement's text and stores it as a TEST_CASE in a child snapshot, linked from the requirement's lineage root; then has CC write a pytest file against that criterion - never from target code - and commits one suite per TEST_CASE (tests/test_<suite>.py, suites/<suite>.suite) to the NRVV project's test-suite repository. Started by the Dispatcher for an NRVV test-author request. |
| nrvv-implementation-1.0 | nrvv | NRVV implementation: one Claude Code session, working only in the NRVV project's target dir and given every test suite, writes the Python implementation that makes the suites pass; a path guard fails the run when anything outside the target dir changed; the implementation is pushed as one commit to the target repository. Started by the Dispatcher for an NRVV implementation request. |
| nrvv-verification-1.0 | nrvv | NRVV verification: checks out the NRVV project's test-suite and target repositories, runs every test suite against the target with pytest, and stores a verdict per suite and per requirement at a named RG snapshot - each suite verdict recomputed from the launcher's facts, so a suite whose listed test did not run never passes - together with the two commits it ran on. Started by the Dispatcher for an NRVV verification request. |
